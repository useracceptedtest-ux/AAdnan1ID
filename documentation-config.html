1. Overview

This documentation describes the configuration and security structure created for a PHP application using a single central file approach. The goal is to keep the application easier to maintain, simpler for future developers, and safer for production usage.

The design is intentionally centralized. This means logic related to database connection, credential validation, token generation, and encryption stays in one place instead of being spread across many files.

This is especially useful when you want to reduce the risk of hidden hardcoded credentials, ensure consistency across the codebase, and make refactoring much easier.

2. Files Created

File Purpose Status
config.php Original single-file app config used earlier Existing file
configPostgreSQL.php PostgreSQL-ready single-file core architecture Created
configPostgreSQL.example.php Human-readable example with setup and usage instructions Created
Important: The original config.php was intentionally left unchanged as requested. The PostgreSQL version was created separately.

3. Why This Centralized Pattern Is Better

  • One source of truth for configuration and logic.
  • Easy to refactor without tracking many scattered files.
  • Safer because secrets are not embedded into source code.
  • New developers can read one file and understand the core idea.
  • More consistent for security validation across database operations.
This structure is especially useful when a team wants a clean and maintainable codebase without needing many small helper files.

4. Secret Management

The system expects secret keys to be stored on the server file system, not inside the project repository. This is important because source code repositories are often shared, backed up, or mirrored.

Recommended folders:

  • Linux: /etc/myapp/keys
  • Windows: C:\myapp\keys
  • Or a separately controlled directory outside the web root

Typical files:

login_secret.key
operation_secret.key
credential_write.key
credential_read.key
user_secret.key
Never place secret files inside the web public folder. Do not put them under nginx/html, wwwroot, or any published web directory.

Windows + Nginx Recommendation

Use a secure folder such as:

C:\secure\keys\login_secret.key
C:\secure\keys\operation_secret.key
C:\secure\keys\credential_write.key
C:\secure\keys\credential_read.key
C:\secure\keys\user_secret.key

5. Database Layer

The PostgreSQL configuration file is designed to support database access in a clean and predictable way. It centralizes database configuration, secure connection creation, and binding of parameter values.

Core responsibilities

  • Read environment variables safely.
  • Build a valid PDO DSN for PostgreSQL.
  • Use prepared statements for SQL safety.
  • Keep a single DB connection object cached in memory.
  • Use transaction boundaries for multi-step writes.

Environment values

DB_DRIVER=pgsql
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=app_db
DB_USER=app_user
DB_PASS=StrongPassword123
DB_CHARSET=utf8mb4
The connection class uses PDO and prepared statements to reduce SQL injection risk and improve maintainability.

6. Read and Write Operations

The config class provides dedicated methods for data access. This makes the system clean and easy to understand for junior developers.

Read methods

  • fetchOne() → one row
  • fetchAll() → many rows
  • streamRows() → large data streaming for memory-safe work

Write methods

  • insert()
  • update()
  • delete()
  • executeWrite()
  • bulkInsert()
For very large data imports, avoid loading all records into memory at once. Use bulkInsert() and streamRows() instead.

7. Token System

The config system keeps two token types separate on purpose:

Token Type Use Important Rule
generateLoginToken() User session / login Used for user authentication, not DB modifications
generateOperationToken() One-time write/delete action Single-use only, different from login token
This separation is critical for avoiding confusion between a user login session and a business operation such as update or delete.

8. Encryption & Decryption

The system includes encryption utilities for both single values and bulk data payloads. All secret keys are expected to be stored outside the repo and outside the public web root.

  • encryptSingle()
  • decryptSingle()
  • encryptBulk()
  • decryptBulk()

This supports scenarios such as:

  • sensitive field encryption
  • secure API payload storage
  • masked or protected data transfers
  • bulk object encryption

9. Windows + Nginx Setup

For a Windows developer using Nginx and PHP, the setup is straightforward if you respect the environment boundaries.

Recommended folder structure

C:\nginx\html\yourapp\
    configPostgreSQL.php
    configPostgreSQL.example.php
    index.php

C:\secure\keys\
    login_secret.key
    operation_secret.key
    credential_write.key
    credential_read.key
    user_secret.key

Important rules

  • Do not store keys under C:\nginx\html.
  • Keep secrets outside the publicly served folder.
  • Use environment variables or a bootstrap file to set values.
  • Enable PostgreSQL PDO support in C:\php\php.ini.
; PHP config
extension=pdo_pgsql
extension=pgsql
If PostgreSQL PDO support is not enabled, the config will fail when trying to connect to the database.

10. Best Practices

  • Use a dedicated database user with minimal privileges.
  • Do not grant superuser permissions to your app database user.
  • Never commit passwords or keys into Git.
  • Always use prepared statements.
  • Use transactions for multi-step writes.
  • Use secure, server-side secret files.
  • Prefer batch processing for very large data imports.
  • Review credential validation before every write operation.

11. Example Flow for a Simple Operation

  1. Application reads env variables.
  2. App opens DB connection.
  3. Developer calls fetchOne() or fetchAll().
  4. For write operations, app verifies credential key.
  5. App generates or validates operation token.
  6. App executes write query with prepared statement.
  7. App commits or rolls back transactions as needed.
  8. App stores/retrieves encrypted payloads from server-side secret-protected files.
require_once __DIR__ . '/configPostgreSQL.php';

$writeKey = AppConfigPostgreSQL::generateCredentialKey('write');

$token = AppConfigPostgreSQL::generateOperationToken(
    'create_user',
    ['name' => 'Ali', 'email' => 'ali@example.com'],
    $writeKey,
    'write'
);

AppConfigPostgreSQL::insert(
    'INSERT INTO users (name, email) VALUES (:name, :email)',
    ['name' => 'Ali', 'email' => 'ali@example.com'],
    $writeKey,
    'write'
);

12. Final Recommendation

The best long-term approach for a team is to keep the configuration logic centralized, with strict secret handling and clear method boundaries. This reduces risk, makes onboarding easier, and gives both junior and senior developers a shared understanding of how the application works.

In short: one core file, secure server-side keys, environment-driven config, strong validation, and proper transaction patterns.

This documentation is meant to be easy for both junior and senior developers to read, maintain, and extend over time.
