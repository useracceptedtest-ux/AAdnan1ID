1. Overview

This documentation explains the PHP configuration and security setup created for this project. It covers both versions created today:

  • config.php for MySQL
  • configPostgreSQL.php for PostgreSQL

The main idea is to keep the application configuration, database access, token rules, credential validation, and encryption logic in a single location to make the system easier to maintain and safer to protect.

A centralized design reduces hidden hardcoded values, makes onboarding easier, and makes refactoring more controlled for both junior and senior developers.

3. MySQL Configuration: config.php

The MySQL version is designed to be a single source of truth for the application. It manages database connection creation, secure read operations, write validation, token generation, and encryption helpers.

Main purpose

  • connect securely to MySQL
  • read one record or many records
  • support SQL operations with prepared statements
  • validate credential keys before writes
  • generate login token and operation token
  • encrypt and decrypt single or bulk data

MySQL environment example

DB_DRIVER=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_NAME=app_db
DB_USER=app_user
DB_PASS=StrongPassword123
DB_CHARSET=utf8mb4
The MySQL version uses MySQL-specific connection configuration and suitable PDO settings, including charset setup and MySQL connection initialization.

4. PostgreSQL Configuration: configPostgreSQL.php

The PostgreSQL file follows the same centralized architecture but uses PostgreSQL-oriented DSN logic and database-safe patterns.

What is different from MySQL

  • PostgreSQL DSN syntax uses pgsql: instead of mysql:
  • default PostgreSQL port is 5432
  • transaction and limit patterns are PostgreSQL-ready
  • streaming and bulk insert pattern is optimized for large data

PostgreSQL environment example

DB_DRIVER=pgsql
DB_HOST=127.0.0.1
DB_PORT=5432
DB_NAME=app_db
DB_USER=app_user
DB_PASS=StrongPassword123
DB_CHARSET=utf8mb4
This PostgreSQL version is designed to be simple for junior developers and powerful enough for large dataset processing.

5. Why This Centralized Pattern Is Better

  • One source of truth for configuration and logic.
  • Easy to refactor without tracking multiple helper files.
  • Safer because secrets are not embedded in source code.
  • New developers can understand the app faster.
  • More consistent security checks before writes happen.

6. Secret Management

The system expects secret keys to be stored on the server filesystem, not inside the project repository. This reduces the chance of credentials being leaked, copied, or exposed through Git history.

Recommended folders:

  • Linux: /etc/myapp/keys
  • Windows: C:\secure\keys
  • or another dedicated folder outside the web root

Typical files:

login_secret.key
operation_secret.key
credential_write.key
credential_read.key
user_secret.key
Never place secret files inside the web public folder. Do not put them under nginx/html, wwwroot, or any published web directory.

7. Database Layer

The config class handles secure connection creation, binds parameters safely, and makes sure business logic does not concatenate raw SQL strings.

Core responsibilities

  • Read environment variables safely.
  • Create a valid PDO DSN for the correct database driver.
  • Use prepared statements.
  • Cache the connection for reuse.
  • Use transaction boundaries for multi-step writes.

8. Read and Write Operations

The config class includes dedicated methods for read and write operations to clarify responsibilities and reduce accidental misuse.

Read methods

  • fetchOne() → one row
  • fetchAll() → multiple rows
  • streamRows() → large dataset streaming

Write methods

  • insert()
  • update()
  • delete()
  • executeWrite()
  • bulkInsert()
This pattern reduces the chance of developers writing raw SQL and directly exposing database operations without validations.

9. Token System

The design separates login token and operation token by purpose.

Token Purpose Important Rule
generateLoginToken() Authentication / user session Do not use for DB write action
generateOperationToken() One-time write or delete action Single-use only
Operation tokens should be validated and invalidated after use. This protects the application from repeated mutation attempts using the same command token.

10. Encryption & Decryption

The config file includes encryption support for single values and bulk payloads. Keys are stored outside the repository for protection.

  • encryptSingle()
  • decryptSingle()
  • encryptBulk()
  • decryptBulk()

This is useful for sensitive operational data, user-specific protected content, and bulk payload transport.

11. Windows + Nginx Setup

This is important because the application may be run on a Windows machine with Nginx and PHP installed separately.

Recommended layout

C:\nginx\html\yourapp\
    config.php
    configPostgreSQL.php
    index.php

C:\secure\keys\
    login_secret.key
    operation_secret.key
    credential_write.key
    credential_read.key
    user_secret.key

Important configuration

; C:\php\php.ini
extension=pdo_mysql
extension=pdo_pgsql
extension=pgsql

For MySQL, ensure the MySQL PDO extension is enabled. For PostgreSQL, ensure the PostgreSQL extension is enabled.

Do not store your secret files under C:\nginx\html or any publicly served folder. The secure key folder must stay outside the web root.

12. Best Practices

  • Use a dedicated app database user with minimal privileges.
  • Never put app secrets in Git.
  • Always use prepared statements.
  • Use transactions for multi-step writes.
  • Keep one method per responsibility.
  • Use key files protected outside the public folder.
  • Use batch insert or streaming for large datasets.
  • Validate credential keys before all write operations.

13. Example Flow

  1. Read environment variables.
  2. Create database connection.
  3. Call fetchOne() or fetchAll() for read actions.
  4. Check credential key before write action.
  5. Generate or validate operation token.
  6. Run the SQL query with prepared parameters.
  7. Commit or rollback transaction if needed.
  8. Store encrypted payloads when necessary.
require_once __DIR__ . '/config.php';

$writeKey = AppConfig::generateCredentialKey('write');

$token = AppConfig::generateOperationToken(
    'create_user',
    ['name' => 'Ali', 'email' => 'ali@example.com'],
    $writeKey,
    'write'
);

AppConfig::insert(
    'INSERT INTO users (name, email) VALUES (:name, :email)',
    ['name' => 'Ali', 'email' => 'ali@example.com'],
    $writeKey,
    'write'
);
require_once __DIR__ . '/configPostgreSQL.php';

$writeKey = AppConfigPostgreSQL::generateCredentialKey('write');

AppConfigPostgreSQL::bulkInsert(
    'users',
    [
        ['name' => 'A', 'email' => 'a@example.com'],
        ['name' => 'B', 'email' => 'b@example.com'],
    ],
    ['name', 'email'],
    $writeKey,
    'write',
    500
);

14. Final Recommendation

The best long-term structure is one central config file, secure secret storage outside the public web directory, environment-driven values, and strict validation before every write operation.

In short: keep the logic centralized, keep the secrets out of the repo, and keep developer onboarding simple with clear method names and comments.

This documentation is intended to be understood by both junior and senior developers and to support safe future refactoring.
